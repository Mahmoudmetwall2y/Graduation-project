# Chapter 5: Conclusion and Future Work

This chapter concludes the AscultiCor graduation project by relating the implemented system and the available evaluation evidence to the objectives defined in Chapter 1. It then identifies the work required to move from an integrated educational prototype toward a reproducible research platform and, only after substantially greater validation, a possible clinically evaluated product. The conclusions are intentionally bounded by the evidence in Chapter 4. Features that exist in source code are described as implemented; measured model results are reported with their evaluated scope; and hardware, deployment, or workflow claims that still lack runtime evidence remain pending.

## 5.1 Project Summary

AscultiCor was developed as an end-to-end platform for acquiring electrocardiogram and phonocardiogram signals, transporting them through an Internet-of-Things architecture, applying artificial-intelligence models, and presenting structured results through a role-aware web application. The project also includes workflow automation for reports, alerts, health monitoring, and operational escalation, together with deployment definitions for the principal services. Its central engineering idea is that cardiac-signal analysis should not be treated as an isolated notebook experiment. Signal acquisition, timing, transport, preprocessing, model contracts, data persistence, access control, presentation, automation, and operational recovery all influence whether an AI result can be used responsibly.

The physical sensing design combines an ESP32-WROOM-32 controller with an AD8232 ECG analog front end and a MAX9814 microphone amplifier for PCG acquisition. The firmware supports distinct ECG and PCG sampling rates, local buffering, binary MQTT publication, device provisioning, session commands, preflight checks, status reporting, and recovery behavior. A custom printed circuit board and portable power architecture were designed around USB Type-C input, lithium-ion charging and protection, source load sharing, a regulated 3.3 V rail, decoupling, test points, and separation of analog and digital concerns.

The AI layer contains three active inference paths. The PCG XGBoost classifier combines traditional signal descriptors with YAMNet embeddings and distinguishes Artifact, Murmur, and Normal recordings. The single-lead ECG model processes prepared waveform windows and RR-related features to classify MIT-style beat categories while exposing auxiliary forecast and experimental risk outputs. The PyTorch murmur-characterization CNN uses four auscultation-position spectrogram channels and returns six heads for timing, shape, grading, pitch, quality, and location. Its delivered checkpoint, six confusion matrices, and runtime architecture are integrated through the same registry and inference service.

The application layer uses Next.js and Supabase to support authentication, organization-aware access, patient and device management, session workflows, signal visualization, predictions, reports, alerts, settings, and administrative operations. n8n workflow definitions cover asynchronous report processing, clinical and device alerts, daily summaries, enrichment, monitoring, and escalation. NGINX, Mosquitto, container definitions, environment templates, health checks, and deployment documentation provide the intended operational structure.

Chapter 4 showed that evidence maturity differs across these components. The PCG model has the strongest aggregate quantitative package. The ECG model has useful selected case studies but lacks aggregate held-out metrics in the delivered folder. Static checks support the quality of parts of the web and inference source, while configured database, automation, deployment, hardware, and complete-session validation still require controlled execution. The correct project conclusion is therefore not that every layer is production-ready, but that the team has built a broad, inspectable prototype and has identified the exact validation steps needed to strengthen it.

The PCG classifier provides the clearest fulfilled AI objective. On the supplied held-out matrix of 1,651 examples, it achieved 83.65% overall accuracy, 82.33% Murmur recall, and 64.60% Murmur precision. The reported Murmur area under the receiver-operating-characteristic curve was 0.915, and Murmur average precision was 0.831. These values show useful screening-oriented discrimination, but the false-positive rate on Normal recordings and the source-dependent recall require further study. The stored threshold sweep also uses 0.243 while the current training and runtime source uses 0.254; the final release must reconcile that difference and regenerate its metrics.

The ECG objective is only partially evidenced. The delivered figures demonstrate selected SVEB, VEB, Fusion, and Unknown examples and show that the artifact produces classification, experimental risk, and forecast outputs. Because the folder lacks a complete held-out confusion matrix, class supports, patient split, and calibration report, no aggregate ECG accuracy is claimed. The objective will be considered quantitatively achieved only when a reproducible patient-disjoint evaluation package is delivered.

The wider software implementation is substantial. Frontend type checking and linting pass, and the inference application compiles. The production frontend source also compiled before prerendering was blocked by absent Supabase public environment variables. Conversely, the database security smoke script detected duplicate migration sequence number 025, `pytest` was unavailable for the model-registry tests, and Docker was unavailable for deployment validation. These results are useful because they define concrete release work rather than leaving integration quality unknown.

The project has not achieved clinical validation, medical electrical-safety certification, regulatory approval, or autonomous diagnostic capability. Those outcomes were outside the responsible scope of a graduation prototype. AscultiCor should continue to be presented as an educational research and decision-support platform whose outputs require qualified human interpretation.

## 5.3 Main Engineering Contributions

The first contribution is a unified multimodal architecture that connects ECG and PCG acquisition to model inference and a structured application workflow. Many prototypes end at a waveform plot or model score. AscultiCor instead defines how a user creates a session, how a device is authorized and commanded, how the device reports preflight and streaming state, how recordings are reconstructed, how model outputs are stored, and how reports and alerts reach the application. This breadth makes cross-team interfaces visible and testable.

The second contribution is the explicit treatment of unequal signal rates and processing contracts. ECG and PCG are not forced into a single generic stream. The device and inference designs retain their distinct sampling, buffering, resampling, filtering, windowing, and feature-generation needs. For PCG, the deployed contract joins traditional features and a YAMNet representation into the exact 1,224-dimensional input expected by the exported scaler and XGBoost model. For ECG, the path resamples device data to the model's 125 Hz target and constructs the waveform and RR-related inputs expected by the delivered Keras artifact.

The third contribution is an inspectable three-model registry with independent loading, configuration, preprocessing, status, and failure behavior. The newly integrated CNN is loaded from a delivered PyTorch state dictionary through a strictly matched architecture and produces six decoded characterization heads. Registry and checkpoint tests verify the current contract, while a disabled configuration remains available as a deliberate operational fallback rather than the default state.

The fourth contribution is a practical custom PCB and power-management design for a portable prototype. The design considers charging, cell protection, simultaneous load behavior, regulation, local decoupling, analog–digital separation, testability, and ESP32 antenna placement. Although electrical characterization remains pending, integrating these concerns into the graduation work is a stronger contribution than relying only on loose development modules without a path toward a repeatable assembly.

The fifth contribution is a tenant-aware web and data architecture. AscultiCor does not treat all users and records as belonging to one undifferentiated account. Authentication, roles, organization boundaries, row-level security, private storage, protected server routes, audit records, and administrative workflows are included in the design. This is particularly important for health-related data, even in a research prototype.

The sixth contribution is the separation of real-time signal transport from asynchronous automation. MQTT and the inference service handle signal and session activity, while n8n coordinates queued reports, notifications, summaries, monitoring, and escalation. This separation prevents an automation engine from becoming the raw biomedical stream processor and makes retry and failure behavior easier to reason about.

The final contribution is methodological: the book distinguishes implemented design, static verification, saved quantitative evidence, blocked checks, and pending measurements. That evidence discipline exposes inconvenient issues such as threshold drift, serialization compatibility warnings, dataset-dependent PCG recall, missing ECG aggregate results, duplicate database migration numbering, and absent hardware measurements. A professional engineering project benefits more from a precise account of these boundaries than from unsupported claims of completeness.

## 5.4 Current Limitations

The hardware limitations are the most immediate barrier to complete system validation. The current evidence does not contain a controlled set of device-acquired ECG and PCG recordings, sample-clock measurements, packet reconciliation, rail-ripple measurements, battery endurance, charger thermal behavior, or source-transition captures. The AD8232 and MAX9814 approach is suitable for an educational prototype, but it is not medically isolated or certified. The microphone automatic-gain behavior and ESP32 radio activity may also influence signal characteristics and must be evaluated on the assembled board.

The AI limitations include incomplete provenance, possible dataset shift, uneven evidence between models, and no prospective validation. The XGBoost result package is useful but lacks the raw prediction export and one script that reproduces all supplied figures. Its saved threshold disagrees with runtime code, and artifact loading produces library-version warnings. The apparent PCG recall difference between data sources indicates that pooled performance is not enough. The ECG package lacks aggregate patient-disjoint metrics and a clear calibration assessment for its confidence and risk outputs. The CNN has six strong confusion matrices but still lacks the raw prediction export, split manifest, calibration analysis, and device-domain case studies required to audit its results fully.

The application and database limitations concern runtime verification and release consistency. Static quality checks do not prove role-based isolation or correct behavior under concurrent sessions. The duplicate migration number must be reconciled with any already-deployed database history. The production build requires a validated environment, and the browser, server routes, Supabase policies, MQTT broker, and inference service still need one correlated integration test.

The n8n limitations are primarily evidential. Workflow definitions exist, but there are no stored execution histories demonstrating success, retry, deduplication, or escalation under controlled failures. LLM report generation also introduces variability, unsupported-statement risk, provider dependence, privacy considerations, and cost. Generated text must be constrained to supplied structured evidence and reviewed by a human.

The deployment limitations include the absence of a repeatable clean-host trial, availability measurements, load tests, security test results, and a demonstrated backup restoration. Plain or publicly exposed MQTT transport would be inappropriate for sensitive use; production device communication should use TLS or an approved private network. Secrets, image versions, dependency versions, and model artifacts must be pinned and governed consistently.

Finally, AscultiCor has not been evaluated as a clinical device. Dataset metrics cannot establish benefit to patients, and a dashboard demonstration cannot establish diagnostic accuracy, safety, usability in clinical practice, or regulatory compliance. The platform should not be used to diagnose, exclude disease, or replace professional assessment.

## 5.5 Future Work

Future work is prioritized by dependency and risk. Immediate work closes contradictions and creates repeatable evidence for the existing prototype. Near-term work improves robustness, data quality, and user workflow. Longer-term work addresses prospective clinical evaluation, interoperability, quality management, and regulated development. This ordering matters: adding more visible features before the existing acquisition and inference chain is reproducibly validated would increase complexity without resolving the most important uncertainties.

### 5.5.1 Hardware and PCB Improvements

The first hardware priority is a formal bring-up and characterization package for the current PCB. The team should test USB-only operation, battery-only operation, charging under load, power-source transition, low-battery behavior, rail ripple, peak Wi-Fi current, analog noise, and thermal behavior. Every measurement should identify the board revision, instrument, probe method, firmware version, and load state. Device sample counts should be compared against an independent timer, and MQTT chunks should be reconciled with locally expected counts.

Signal acquisition should be evaluated using controlled sources before relying on volunteer recordings. An ECG simulator or safe low-voltage waveform source can test bandwidth, saturation, lead-off behavior, and repeatability. A controlled acoustic fixture can play reference heart-sound recordings into the chest piece and help separate microphone, coupling, ambient-noise, and preprocessing effects. Human recordings, if approved, should follow an ethical protocol and record electrode placement, body position, chest location, device revision, and environmental conditions.

A later PCB revision should consider an external higher-resolution ADC where justified by measured noise, stronger analog filtering, improved grounding and shielding, more robust connectors, battery gauging, electrostatic-discharge protection, and hardware-level fault indication. The enclosure should provide strain relief, consistent acoustic coupling, safe battery retention, cleaning considerations, and clear electrode and control labeling. Any path toward clinical use would require a fundamentally stronger safety architecture, including appropriate isolation, leakage-current analysis, biocompatibility considerations, and testing against applicable medical-device standards.

### 5.5.2 AI and Dataset Improvements

The PCG release should first be made reproducible. The team should choose the intended Murmur threshold, remove the 0.243 versus 0.254 mismatch, and regenerate the confusion matrix and curves from the exact runtime decision rule. The release package should include patient split files, raw held-out probabilities, feature-order manifest, dataset versions, random seeds, environment lock file, native XGBoost export, artifact hashes, and a one-command evaluation script. Per-source, leave-one-source-out, and confidence-calibration results should be added.

Improvement should focus on diversity rather than only volume. Recordings from different devices, chest locations, environments, demographics, and clinical settings are needed to assess whether the classifier learns cardiac characteristics or source-specific shortcuts. Hard Normal–Murmur examples and realistic artifacts should be reviewed systematically. Threshold selection should reflect a predefined use case and should report the practical false-positive burden as well as sensitivity.

The ECG team should deliver a complete patient-disjoint evaluation for all five beat classes. Required outputs include class supports, confusion matrix, precision, recall, F1-score, calibration, subject-level variability, and representative failures. Normal examples must be included. Beat classification, forecast reconstruction, and risk estimation should be reported as separate tasks with distinct labels and validation criteria. The experimental risk head should not be displayed as a clinical percentage until its target definition, cohort, discrimination, calibration, and external validation are established.

The active murmur-characterization CNN should now be strengthened rather than activated. The team should freeze a signed model manifest specifying the checkpoint hash, 22,050 Hz preprocessing, 128 × 216 mel representation, four-channel order, six label mappings, dataset and patient split, library versions, and runtime version. Raw per-example predictions should accompany the six confusion matrices so precision, recall, F1, uncertainty, calibration, and source-stratified behavior can be reproduced. The forthcoming runtime test cases should cover correct valve metadata, missing metadata, the replicated-channel fallback, XGBoost non-Murmur gating, and representative failures on MAX9814 recordings.

Longer-term AI work may explore multimodal fusion between ECG and PCG, explainability that maps outputs to interpretable signal regions, uncertainty-aware rejection, continual drift monitoring, and privacy-preserving collaborative learning. These approaches should follow, not replace, strong baseline provenance and external validation.

### 5.5.3 Application and Automation Improvements

The application should gain a repeatable automated test stack covering unit, route, database-policy, component, and end-to-end behavior. The immediate release tasks are to pin the Python test environment, execute the model-registry suite, resolve duplicate migration numbering safely, add a pre-build environment validator, and run the frontend build with a disposable configured Supabase project. Authorization tests should use multiple organizations and every supported role to prove both allowed and denied actions.

Live-session testing should cover command duplication, device timeout, partial recordings, browser reconnection, two simultaneous viewers, repeated stop requests, model unavailability, and persistence failure. The user interface should expose data quality, model status, incomplete-session state, and confidence limitations in plain language. AI results should link to the recording and preprocessing version that produced them.

A formative usability study should measure task completion, time, errors, assistance, comprehension, and accessibility for patient management, device assignment, session control, result review, report handling, and alert acknowledgement. Findings should guide navigation, terminology, visual hierarchy, keyboard support, contrast, responsive layout, and recovery messages. The goal is not cosmetic polish alone but reduced operational error.

Every n8n workflow should receive success-path and failure-injection tests. Idempotency keys, retry limits, dead-letter or failed states, deduplication, escalation rules, and audit references should be explicit. LLM reports should use structured input, bounded prompts, schema validation, evidence citation, prohibited diagnostic language, and human approval where appropriate. Provider failures must not block the underlying prediction or session record.

### 5.5.4 Cloud, Security, and Clinical Validation

The cloud environment should be rebuilt from a clean host using pinned images and a documented release manifest. The team should validate HTTPS, MQTT protection, private service networking, least-privilege credentials, secret rotation, log retention, health checks, restart behavior, monitoring, and alert routing. Load testing should characterize CPU, memory, disk, network, model latency, concurrent sessions, and storage growth. A backup should be restored into a separate environment and reconciled with the source records.

Security work should include cross-tenant attempts, storage-policy tests, modified and expired tokens, internal-route authorization, MQTT topic isolation, dependency scanning, secret scanning, rate limiting, audit-log integrity, and incident-response rehearsal. Privacy controls should define data minimization, retention, deletion, access review, and handling of model or LLM provider requests.

If the project progresses beyond education and research, future clinical work should begin with an approved study protocol and clearly defined intended use. Reference labels should be produced by qualified professionals with adjudication rules, and performance should be reported with confidence intervals and clinically meaningful endpoints. Usability, human factors, fairness across relevant groups, calibration, false reassurance, alarm burden, and workflow impact require prospective study. Regulatory classification, quality management, risk management, software lifecycle controls, cybersecurity, electrical safety, and post-market responsibilities would need specialist guidance.

## 5.6 Final Remarks

AscultiCor demonstrates what can be achieved when hardware, embedded, AI, web, automation, and infrastructure teams work around explicit interfaces rather than isolated deliverables. The project has produced a coherent platform design, substantial implementation, a custom hardware path, deployed-model contracts, application workflows, and meaningful quantitative PCG evidence. It also exposes the real difficulty of integrated biomedical engineering: the final result is only as trustworthy as the connection between acquisition conditions, data provenance, model evaluation, runtime configuration, access control, and operational evidence.

The most important next step is not to make the prototype appear finished. It is to make the existing system reproducible and measurable. Resolving the PCG threshold mismatch, delivering aggregate ECG results, completing the CNN manifest and runtime test cases, characterizing the PCB, fixing migration history, executing the remaining tests in pinned environments, and capturing a complete session trace will materially strengthen the project.

Within its stated boundaries, AscultiCor is a credible graduation project and a strong base for continued research. It should be presented confidently for its genuine contributions and cautiously where evidence is incomplete. That combination—ambitious integration with disciplined claims—is the foundation on which any later clinical or commercial work must be built.
