3.4.1 Database Migration History Narrative

The foundational architecture of the Supabase PostgreSQL database evolved progressively across 28 distinct SQL migrations, mirroring the iterative development of the AscultiCor platform. This robust migration strategy, managed via the Supabase CLI, ensures that the database schema can be deterministically reproduced in local development, staging, and production environments, eliminating the "works on my machine" anti-pattern.

Migrations 001 through 005 established the core entity relationships. The `organizations` table was created as the root tenant boundary, followed by the `devices` and `profiles` tables. Every entity in the system includes an `org_id` foreign key, establishing a strict multi-tenant architecture. Migrations 006 through 010 introduced the clinical features: the `patients` table, featuring a globally unique Medical Record Number (MRN) constraint per organization, and the `sessions` table to track individual diagnostic encounters. 

The most significant security hardening occurred between migrations 011 and 020, where the Frontend team implemented PostgreSQL Row-Level Security (RLS) policies across all tables. These policies enforce tenant isolation at the database kernel level; a user authenticated via a Supabase JWT can only SELECT, INSERT, or UPDATE rows where the `org_id` matches their profile's organization. This eliminates the risk of application-level routing bugs exposing cross-tenant data. 

Migrations 021 through 028 focused on IoT security and device isolation. The `devices` table was augmented with `mqtt_username` and encrypted `mqtt_password_hash` columns. The frontend team developed a secure bootstrap workflow where devices receive these credentials upon first boot. Concurrently, Mosquitto's ACLs were configured to restrict each device's MQTT publish/subscribe permissions strictly to its own topic namespace (e.g., `org/[org_id]/device/[device_id]/#`). This ensures that even if a device is physically compromised and its flash memory extracted, the attacker gains access only to that specific device's data stream, preventing lateral movement across the organization's sensor fleet.

3.4.3 API Architecture and Dual Authentication

The AscultiCor platform exposes a suite of API endpoints to facilitate communication between the Next.js frontend, the FastAPI inference service, and the n8n automation engine. Securing this communication required a dual-authentication architecture designed to accommodate both human users and automated services.

For human users accessing the Next.js clinical dashboard, authentication is handled natively by Supabase Auth. Upon successful login, the client receives a short-lived JSON Web Token (JWT) containing the user's UUID and `org_id`. This JWT is attached as a Bearer token to all subsequent API requests. The Next.js API route handlers verify the JWT signature using the Supabase JWT Secret. Because the Supabase client is instantiated with this user-specific JWT, all subsequent database queries automatically inherit the user's RLS context, ensuring data isolation.

For service-to-service communication—such as the n8n workflow engine requesting the Next.js API to process pending LLM reports, or the FastAPI inference service updating a session status—JWTs are impractical as there is no interactive login. Instead, the backend exposes specific service endpoints protected by an Internal API Token mechanism. Requests to these endpoints must include an `x-internal-token` HTTP header matching a high-entropy secret securely shared between the containers via environment variables (`ASCULTICOR_INTERNAL_API_TOKEN`). 

When a request is authenticated via the internal token, the Next.js API instantiates the Supabase client using the `service_role` key. This special key bypasses all RLS policies, granting the API full administrative access to the database. This design allows automated background tasks to query across all organizations (e.g., compiling the daily digest or processing alerts) without being artificially constrained by a single user's permissions, while keeping the public-facing dashboard strictly bound by RLS.
